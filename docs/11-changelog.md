# Future Release Format

Future entries should follow this structure:

```text
# [Version] — Release Name

**Date:** YYYY-MM-DD

## Added

- New features or sections.

## Changed

- Existing functionality or design changes.

## Improved

- Performance, accessibility, UX, or visual improvements.

## Fixed

- Bugs and defects resolved.

## Tested

- Testing performed.

## Deployment

- Production deployment information.
```

---

# Change Categories

Velocity changes should be categorized using the following terms.

## Added

For completely new functionality or content.

Example:

* Added vehicle collection section.

---

## Changed

For modifications to existing behavior or design.

Example:

* Changed hero layout for tablet screens.

---

## Improved

For quality improvements.

Example:

* Improved image loading performance.

---

## Fixed

For defects.

Example:

* Fixed mobile navigation overflow.

---

## Removed

For functionality or content intentionally removed.

Example:

* Removed unnecessary gallery animation.

---

## Security

For security-related changes.

Example:

* Removed accidentally exposed configuration.

---

## Documentation

For documentation changes.

Example:

* Updated responsive design specification.

# Release Principles

Each release should represent a meaningful project milestone.

Before marking a release as complete:

1. Relevant functionality is implemented.
2. Testing has been performed.
3. Known critical defects are resolved.
4. Documentation is updated.
5. Git history reflects the changes.
6. Production status is recorded where applicable.

# Changelog Maintenance Rule

The changelog should be updated when a meaningful project change is completed.

Do not record every tiny CSS adjustment.

Record changes that help someone understand the evolution of the project.

The changelog should answer:

**What changed?**

**Why did it change?**

**When did it change?**

**Which version contains the change?**
